### B-2. ✅ 해결 — 3-14 수치는 맞다. 문제는 **캡처 간 재현성**이었다

10/27 원본 데이터에 오늘의 `len_control.py`를 돌린 결과 **0.874 / 0.958 / 1.000** 으로
3-14 가 적은 값이 그대로 재현됐다. **계산 방식도 수치도 틀리지 않았다.**

진짜 문제는 **다른 날 찍은 캡처에서 안 나온다**는 것이고, 그게 채널마다 다르다:

| 채널 | 10/27 | 11/3 | 변동 |
|---|---|---|---|
| `down_bytes` | 1.000 / 0.992 / 0.933 | 0.981 / 0.985 / 0.949 | **±0.02** |
| `pkt_gap_ms` | 0.874 / 0.958 / 1.000 | 0.714 / 0.991 / 0.845 | **±0.16** |

원인은 망 지터다. 추론 0 콜의 `pkt_gap` IQR 이 1글자 258→1,247ms, 긴 설명 222→1,453ms 로
커졌고, **지터가 그대로였던 짧은 설명(261→257ms)에서만 AUC 가 올랐다.** 세 arm 전부 대응한다.

→ **HANDOFF 3-22 로 기록**. 3-14 머리에 재현 실패 경고를 달고,
  "답이 길수록 오른다 → 1.000"을 발표에 쓰지 못하도록 막았다.

**부수 효과 — A-2 가 함께 해소됐다.** 3-14 가 금지했던 `down_bytes` 가
오히려 **캡처 간 재현되는 유일한 채널**로 드러났다. 금지를 해제하고 반대 단서를 달았다
("`pkt_gap_ms` 단독 보고가 오히려 위험하다").

## D. 새로 생긴 한계 — 기록은 됐으나 눈에 안 띔 (3건)

### D-1. `timing-only` 정본의 의미가 provider마다 다르다

```
Groq   : timing-only == packet-down (전 arm에서 한 건도 안 다름)  → '정본'이 곧 최선
Gemini : timing-only 0.867  <  packet-down 0.983 (긴 응답)        → '정본'은 보수적 하한
```

같은 "정본"인데 한쪽은 최선이고 한쪽은 하한이다. 발표에서 한 숫자로 묶으면 오해를 부른다.
(3-20(g)에 적어뒀으나 1장·7장에는 반영 안 됨.)

### D-2. 3클래스는 arm 간 비교에 쓸 수 없다

답을 길게 쓰라고 하면 `think_high`가 더 많이 추론해(Groq 224→251→295) `med`와의 간격이
벌어져 **문제가 쉬워진다**. 실제로 Groq 3클래스는 1자 0.674 → 123자 0.888로 **올라간다**.
길이 효과가 아니다. (3-20(h)에 기록. 이진은 간격이 벌어졌는데도 떨어지므로 안전.)

### D-3. provider 둘로는 메커니즘을 못 가른다

Gemini ≠ Groq인 것이 서명 전송 말고도 모델·스트리밍 구현·청크 크기·서버 위치로 여러 개다.
교차 비교로 "서명 때문"을 주장하면 교란을 결론으로 둔갑시키는 것이 된다.
근거는 전부 **Gemini 내부**에서 와야 한다(3-16 r=0.996, 3-17 잔차 0.998, 3-20(d) 피처 중요도).
(3-20(d-2)에 기록.)
