## 핵심 요약
암호화(TLS) 상태의 **멀티프로바이더·멀티모델 LLM API 트래픽**에서 reasoning effort(low/high)를
탐지하는 연구의 정식 설계본. 선행 L4 파일럿(단일모델·Gemini/Groq에서 추론깊이 누출 실증, E1 96%)을
**여러 provider·model로 확장**하고, configured effort와 realized reasoning token을 분리한 이중
ground truth·model identification 분리·cross-model 일반화·early detection까지 포함한다.
핵심 방어축은 "이게 그냥 duration/TTFA 재포장 아니냐"와 "reasoning 아니라 provider fingerprint
아니냐"를 정면으로 막는 것.

## 연구 질문 (RQ)
- RQ1: 동일 모델·동일 프롬프트에서 low/high effort가 구별되는 네트워크 패턴을 만드는가?
- RQ2: 어떤 신호가 effort를 가장 잘 나타내나? (단, 스트리밍 가시성 그룹별로 답이 갈림 — 아래)
- RQ3: 새 prompt/날짜/네트워크에 일반화되나?
- RQ4: provider·model 간 탐지 성능 차이는?
- RQ5: 한 모델서 학습한 탐지기가 미학습 모델서도 되나? (cross-model)
- RQ6: 응답 완료 전에 얼마나 일찍 판단 가능한가? (early detection)

## 세 가지 Task (반드시 분리)
- Task A: configured effort 탐지 f(X) → {Low, High}. label = API effort 설정값.
- Task B: realized reasoning 추정 g(X) → reasoning token 수. label = API usage의 실제 thinking token.
- Task C: model identification h(X) → model. 목적 = 모델 자체 fingerprint 세기 측정.
- A와 C를 분리해, effort 탐지기가 단순 모델 fingerprint를 쓰는 게 아닌지 검증.

Groq 120콜 쓸기에서 **최대 패킷 간격 = 첫 간격**인 콜이 110/120(92%)이었다. 짧은 설명 조건은 24/24(100%).
즉 추론 멈춤은 응답 전체에 흩어지지 않고 **첫 응답 패킷 직후 한 군데에 통째로** 있다.

| | 침묵 위치 | 포착 피처 | 3차 단일 AUC |
|---|---|---|---|
| Gemini | 첫 패킷 **이전** | `pkt_gap_ms`(요청→첫응답) | 0.890 |
| Groq | 첫 패킷 **이후** | `down_iat_first_ms`(첫 간격) | — (신규) |

- `pkt_gap_ms`가 Groq에서 무용지물(0.49)이던 이유가 이걸로 설명된다 — 첫 패킷이 추론과 무관하게 ~300ms 고정
- "채널이 이동한다"보다 단순하고 강한 설명. **양쪽 다 추론량에 비례하는 단일 침묵**이고 기준점만 다르다
- 관련: [[생성형AI 트래픽 식별 — L4 연구 로드맵]]의 "응답 전 침묵 구간" 피처 설계가 Groq에선 기준점을
  첫 패킷으로 옮겨야 한다는 뜻

### 평균 간격은 긴 응답에서 신호를 지운다 <!-- (2026-10-27) -->
추론 멈춤은 응답당 사실상 한 번인데, 답이 길면 간격이 수백 개가 되어 평균에 묻힌다.
`think_high` 기준 실측(Groq 120b):

| 응답 길이 | 추론 토큰 | 첫 간격 | 평균 간격 |
|---|---|---|---|
| 1글자 | 210 | 548ms | 183.7ms |
| 짧은 설명(142자) | 286 | 1,912ms | 32.9ms |
| 긴 설명(868자) | 571 | **4,017ms** | **16.5ms** |

**평균은 떨어지고 첫 간격은 오른다 — 방향이 반대다.** 평균만 쓰면 "긴 응답에선 신호가 죽는다"는
틀린 결론에 도달한다. → `parse_pcap.py`에 `down_iat_max_ms`·`down_iat_p90/p99_ms`·
`stall_total_ms`·`stall_count`·`down_iat_first_ms` 6개를 추가했다.

⚠️ 단 **정량 관계는 미확정**. 조건 안에서 추론 토큰과의 순위상관이 0.11~0.50으로 약하다.
조건당 8콜 + 아래 오염 때문이며, 깨끗한 캡처로 다시 재야 한다.

### `A_len`(응답 길이) 파일럿 — 설계 결함 3건 <!-- (2026-10-27) -->
> 명명 주의: 처음에 이 실험을 "E4"라 불렀으나 **E4는 이미 해상도(=Task B)였다.**
> 2026-10-27부터 E 번호를 폐기하고 **Task A/B/C + 조건 축**으로 통일했다. HANDOFF 1-1 참조.
"답이 길어져도 추론이 탐지되나"를 재려고 응답 길이를 쓸었다. 본실험 전에 돌린 게 정답이었다.

1. **고정 문자열 arm 폐기.** 길이를 통제하려고 `ABCDEFGHIJ`를 N번 반복시켰는데,
   모델이 횟수를 못 센다(1,601자 지시 → 10,825자 출력, 준수율 **0/24**). 게다가 세느라
   **추론 토큰을 5배**(131→691) 쓴다. 측정 대상을 실험 조작이 오염시키는 꼴이라 폐기.
2. **arm 혼합 캡처 금지.** 5개 arm을 한 캡처에 섞어 무작위로 돌렸더니, 거대 응답 바로 뒤에 온
   짧은 콜의 간격이 1,000~2,100ms로 튀었다(정상은 30ms대). 앞 콜 꼬리·연결 재설정이
   다음 콜 측정창에 섞인 것. 이 때문에 1글자 조건이 3차(AUC 0.997)를 재현 못 했다(0.625).
   → **본실험은 arm 별로 분리 캡처.**
3. **자유 응답이면 길이 통제가 저절로 된다.** `free_brief`에서 답변 토큰이
   low 97.5 / med 111.5 / high 98 로 **추론 수준과 무관**했다. "추론 많이 하면 답도 길어진다"는
   우려가 짧은 응답에선 성립하지 않는다. 억지 고정 장치가 불필요하다는 뜻.
   (긴 응답 `free_full`은 573/492/687로 비단조 — n=8이라 **판정 보류**.)

→ 본실험 조건은 **1글자 / 짧은 설명 / 긴 설명** 3개, 전부 자연 응답, arm별 분리 캡처.

### 쿼터가 실험 규모를 제약한다 <!-- (2026-10-27) -->
- **Groq 무료 티어 일일 토큰 한도 200,000(조직 단위, 키 단위 아님).** 이날 소진돼 본실험이 65/180에서 중단.
  쓸기 실험의 폐기 대상 arm 2개(`400`·`1600`)가 **113,673토큰, 전체의 71%**를 먹은 게 원인.
- 실측 콜당 토큰(입력 300 포함): 1글자 450 / 짧은 설명 606 / **긴 설명 1,294**.
  원안(30문항×3조건×2반복×3arm=540콜)은 **423,000토큰 = 한도의 2.1배**.
- **날짜를 쪼개 돌리면 안 된다** — arm과 날짜가 교락되어 arm 간 비교가 불가능해진다. 3조건은 같은 날 연속으로.
- 유료 전환 시 비용: `gpt-oss-120b` 입력 $0.15 / 출력 $0.60 per 1M → 원안 전체 **약 $0.18**.
  (단가는 `console.groq.com/docs/models`에서 확인. `groq.com/pricing`엔 단가가 없어 교차검증 불가.
   Dev tier의 TPD는 문서 간 수치가 충돌해 **확인 못 함** — 계정 `/settings/limits`에서 봐야 한다.)

### ⭐ 바이트 미스터리 규명 — 암호화된 사고 서명이 길이로 샌다 <!-- (2026-11-03) -->
30문항 × 3조건 × 1반복 = 90콜(`gem_strict_sigtest`, 에러 0). 파싱 코드가 `if not txt: continue` 로
건너뛰던 **텍스트 없는 content 파트**를 열어보니 `thoughtSignature` 가 들어있었다.
Gemini 3 계열이 멀티턴에서 추론 맥락을 유지하려고 **내부 사고를 암호화해 되돌려주는** 값이다.

내용은 못 읽는다. 그런데 **길이가 안 가려진다.**

- **추론 토큰 → 서명 길이**: 피어슨 **0.996** (n=90). 추론 0 이면 `sig_chars` 가 **예외 없이 98자**,
  추론이 조금이라도 있으면 최소 333자. 약 4.0자/추론토큰.
- **서명 길이 → 관측 가능한 바이트**: `down_bytes = 1.511 × sig_chars + 1183.4`, **r = 0.9977**
  (n=89, 첫 콜 1건은 핸드셰이크가 창에 섞여 제외). 기울기 1.51 = base64(1.333) + 프레이밍·TLS 오버헤드.
  **사슬이 닫혔다** — 앱 레벨 숫자가 아니라 네트워크 관측자가 보는 값으로 이어진다.
- **바이트 하나로 추론 유무 완전 분리**: 추론 없음 1,370~1,373바이트(폭 4), 추론 있음 1,737~12,591.
  겹침 0, 간격 364바이트 → **AUC 1.000**. 양도 샌다: `down_bytes = 5.68 × 추론토큰 + 1135.5` (r=0.9922).

누출 경로가 타이밍 하나에서 **둘**이 됐고, 둘째가 훨씬 정확하다(침묵 순위상관 0.65 vs 서명 0.996).
서술: **"구현이 의도적으로 숨긴 것이, 숨기는 방식 자체 때문에 샌다."**
내용 기밀성(암호화)과 메타데이터 기밀성(길이)은 별개 문제다.

**반드시 같이 쓸 단서 3개** (안 쓰면 과장이다):
1. 답을 1글자로 고정했기 때문이다. 실전에선 답 길이가 바이트를 지배해 분리가 깨진다. **상한**이지 실전 성능이 아니다.
2. `think_low` 30콜 중 대부분이 `sig_chars=98` — 추론을 아예 안 했다. low/high 가 아니라 사실상 **0 vs >0** 대비다.
   위 "설정(configured)은 깊이를 거의 못 나타낸다" 항목과 같은 결론.
3. **패딩 한 줄이면 막힌다.** "뚫었다"가 아니라 "왜 아직 아무도 안 막았나"가 논점이어야 한다.

- 관련 파일: `out/gem_strict_sigtest_log.jsonl` · `out/gem_sigtest.csv` · `out/gem_strict_sigtest_20261030_052926.pcap`
- 계측 코드: `capture_run_strict.py` 의 `sig_chars`/`sig_parts`/`parts_no_text`
- 관련: [[생성형AI 트래픽 식별 — L4 연구 로드맵]]

### 게이트웨이는 추론 토큰을 안 준다 — 위협모델의 두 번째 다리  <!-- (2026-11-16) -->
[[BAZE 게이트웨이 vs Gemini 직결 — 수집 환경 비교]]에 **측정 제약**으로 적어둔 사실(`completion_tokens_details: null`)에는
**위협모델 쪽 의미**가 따로 있다. 그쪽은 "그래서 Task B 라벨을 직결에서 받아야 한다"는 우리 사정이고,
여기 적는 건 "그래서 게이트웨이 고객은 검증할 수단이 없다"는 피해자 사정이다.

실측(2026-11-16 재집계):

| 경로 | `thoughts_tokens` 없음 | 의미 |
|---|---|---|
| 직결 (Gemini 네이티브) | 71 / 1,020 (15.3%) | **추론을 안 했다.** 0이라 필드가 생략됐다. 71건 전부 `think_low` |
| 게이트웨이 (BAZE, OpenAI 호환) | 1,020 / 1,020 (100%) | **안 알려준다.** 생각은 했는데 숫자를 주지 않는다 |

**로그에서 둘 다 `null` 로 보이지만 섞으면 안 된다.** 전자는 정보(추론량 0)고 후자는 정보 부재다.
분석 코드에서 `thoughts_tokens == null` 을 0 으로 치환할 때 경로를 구분하지 않으면
게이트웨이 데이터 전체가 "추론 0"으로 둔갑한다.

**왜 이게 동기가 되나.**
직결 사용자는 `low` 로 걸고 응답에 `thoughts_tokens=968` 이 찍히면 "설정보다 깊게 돌았다"를 **그 자리에서 안다.**
패킷을 볼 이유가 없다 — `capture_run_strict.py:314` 가 `usage_metadata.thoughts_token_count` 를 그냥 읽는다.
그래서 "나도 모르게 토큰이 샌다"는 **직결에서는 성립하지 않는다.**

게이트웨이 고객은 같은 일을 못 한다. 크레딧은 콜당 약 2.44 씩 빠지는데
얼마나 생각했길래 그만큼 빠졌는지 확인할 경로가 **응답 안에 없다.**
여기서 트래픽이 유일한 독립 검증 수단이 된다. 위 [이 연구는 왜 하는가] 의 (B) 가 서는 지점이 정확히 이것이다.

**아직 확인 못 한 것:** 이게 BAZE 한 곳의 구현인지, OpenAI 호환 게이트웨이 일반의 양상인지 모른다.
BAZE 외 게이트웨이를 안 재봤다. 논문에 "게이트웨이는 안 준다"로 일반화하려면 **최소 2~3곳을 더 확인해야 한다.**
추론 토큰을 받는 옵션·헤더가 있는지도 아직 안 찾아봤다(BAZE 노트 "다음 할 일"에 걸려 있음).

### 이 연구는 왜 하는가 — 동기 4개의 강도 정리  <!-- (2026-11-16) -->
구두로 정리하다 동기가 뒤섞여서 세기 순으로 다시 세운다. **넷 다 맞는 말이지만 논문의 척추가 되는 건 하나뿐이다.**

**(A) 제3자 부채널 — 척추.** 관측자는 API 사용자가 **아니다.** TLS 암호문만 본다.
그런데도 "이 질문에 모델이 얼마나 깊이 생각했는가"가 새어 나온다. 추론 깊이는 **질문의 난도·민감도와 상관**하므로,
내용을 못 읽어도 질문의 성격이 샌다. 이게 보안 논문이 되는 이유다.
현재 실험 설계(답 1글자 강제, 요청 바이트 패딩 통제, timing-only 지표)는 **전부 이 질문에 맞춰져 있다.**

**(B) 사용자가 설정과 실제를 대조 못 하는 구간 — 두 번째로 강함.** "low 로 걸었는데 실제론 깊게 돌 수 있다"는
이미 우리 데이터로 확정됐다(위 [설정(configured)은 깊이를 거의 못 나타낸다], `think_low` 의 83%가 추론 0).
다만 **직결로 부르면 `usage` 에 추론 토큰이 찍히므로 트래픽을 볼 이유가 없다.**
이 동기가 살아나는 조건은 **usage 를 못 믿거나 못 볼 때**다:
- 게이트웨이 경유. BAZE 1,020콜 전부 `thoughts_tokens = null` 이다. 재판매 고객은 추론 토큰을
  **원천적으로 확인할 수 없다.** 근거와 한계는 위 [게이트웨이는 추론 토큰을 안 준다] 항목.
- 자기보고 검증. `usage` 는 과금 주체가 스스로 적은 숫자다. 외부 측정으로 교차검증할 수단이 없다.

**(C) 깊이가 깊어질수록 트래픽이 어떻게 변하는가 — RQ1·RQ2 그 자체.** 이건 동기가 아니라 **연구 질문**이다.
지금까지 답: 침묵으로 수렴하지 않고 **간격으로 이동**하고(가시성 축 실측), 바이트로도 샌다(사고 서명 기록).

**(D) 토큰 비용 — 배경이지 기여가 아니다.** 실측하면 Gemini 3.5 Flash-Lite 에서 **high 가 low 의 7배**다
(콜당 0.07c vs 0.52c, [[LLM API 요금·무료한도 비교]]). 설정 하나로 비용이 7배가 되는 건 사실이다.
그러나 심사자는 "비용 문제면 `usage` 읽으면 끝인데 왜 패킷을 보나"라고 묻는다. **(B)의 조건이 붙어야만 반박된다.**
비용은 "왜 이 설정값이 중요한가"의 **맥락**으로 쓰고, 기여로 내세우지 마라.

**순서 주의.** 비용을 앞세우면 논문이 아니라 FinOps 블로그가 된다. (A)를 앞에 세우고,
(B)를 게이트웨이 증거와 함께 붙이고, (D)는 "그래서 이 설정값은 돈이 걸린 값이다" 한 줄로 쓴다.

**지금 설계로 (D)를 주장할 수 없는 이유도 적어둔다.** 우리는 답을 1글자로 강제했다.
실제 서비스는 긴 답을 뱉으므로 비용 구조가 다르다. 비용을 기여로 쓰려면 `A_len` 계열 조건으로 다시 재야 한다.

### 481문항 확장 — 서명 기전·패딩 통제 재확인 (n=90 → n=1,443) <!-- (2026-11-17) -->
Gemini `gemini-3.5-flash-lite`, 481문항 × 3조건(`think_low`/`think_medium`/`think_high`)
= **1,443칸 전부 측정**, 잘림 2건.

**⚠ "전수"가 아니다.** v2 는 **821문항**이고 이 묶음은 그중 **481문항(58.6%)** 이다.
무료 등급 일 500콜 제한에 걸려 며칠에 나눠 받다가 481 에서 멈춘 것이다.
"1,443칸 전부"는 **그 481문항이 3조건을 빠짐없이 갖췄다**는 뜻이지 문항셋 전체가 아니다.
논문에 쓸 때는 "v2 821문항 중 갈래를 가로질러 추출한 481문항"으로 적어야 한다.

### ⭐ 단계 해상도의 진짜 한계 — 양극은 결정적, 인접은 동전 던지기 <!-- (2026-11-19) -->

### ⭐ 서명 없는 OpenAI 가 Claude 보다 10배 많이 샌다 <!-- (2026-11-20) -->
**OpenAI 3모델은 `thoughtSignature` 에 해당하는 필드를 아예 안 보낸다** — 3,750콜 전부 `sig_chars=0`.

**다음 확인:** 원시 SSE 이벤트를 저장해 OpenAI 가 추론 중 무엇을 흘리는지 본다(1콜이면 충분).

### Task A/B/C 공통축 성적 <!-- (2026-11-20) -->
**공통축 = 250문항 × 3단계(low/medium/high)**, 순응·비잘림·1자 답만.
분할은 **문항 단위 2폴드 교차검증**이다. 행 단위로 쪼개면 같은 문항이 학습·시험에 동시에 들어가 부풀려진다.
**피처는 전선 관측 가능한 것만** 쓴다(`down_bytes` `app_ttft_ms` `stall_total_ms` `down_pkts` `chunk_count`).
`sig_chars`·`thoughts_tokens`·`output_tokens` 은 API 응답 필드라 공격자가 못 본다 — 제외.

**Task A (설정 탐지)** — A1 = 단일 콜·문항 모름(가장 현실적), A2 = 같은 문항 인접 두 조건, A3 = 전 단계 순서

| 모델 | A1 3분류 (우연 33%) | A2 인접쌍 (50%) | A3 전순서 (17%) | 추론토큰 L/M/H |
|---|---|---|---|---|
| gemini-3.5-flash-lite | **64.7%** | **92.5%** | **85.5%** | 93 / 717 / 1,221 |
| claude-sonnet-5-5 | 62.6% | 76.1% | 52.1% | 75 / 156 / 255 |
| claude-haiku-5-5 | 47.5% | 76.4% | 54.9% | 217 / 317 / 436 |
| gpt-6.1-terra | 43.3% | 75.0% | 54.8% | 51 / 90 / 122 |
| gpt-6.1-sol | 40.7% | 81.4% | 64.0% | 42 / 55 / 103 |
| claude-opus-5-5 | 36.5% | 67.0% | 37.7% | 158 / 215 / 221 |
| gpt-6-luna | 35.6% | 67.1% | 41.0% | 137 / 207 / 255 |

**A1 순위가 추론토큰 격차 순위와 거의 같다.** 탐지 난이도는 탐지기가 아니라 **모델이 단계를
얼마나 벌려 쓰느냐**가 정한다. Gemini 가 압도적인 건 low→high 가 13배(93→1,221)로 벌어지기 때문이다.
opus 가 꼴찌인 건 medium 215 vs high 221 로 **두 단계를 사실상 같게 쓰기** 때문이다.

**Task B (실현 추론량 회귀)** — log 공간 다중회귀, 문항 단위 2폴드. 5단계 전량 기준.

| 모델 | R²(log) | 중앙 절대오차 | 상대오차 중앙 | `down_bytes` 단독 R² |
|---|---|---|---|---|
| claude-haiku-5-5 | **0.977** | 27 tok | 9% | 0.827 |
| claude-sonnet-5-5 | 0.964 | 31 tok | 11% | 0.784 |
| gemini-3.5-flash-lite | 0.936 | 104 tok | 14% | 0.905 |
| gpt-6.1-terra | 0.928 | 16 tok | 21% | 0.746 |
| gpt-6-luna | 0.917 | 17 tok | 19% | 0.776 |
| gpt-6.1-sol | 0.887 | 13 tok | 25% | 0.700 |
| claude-opus-5-5 | 0.878 | 23 tok | 13% | 0.752 |

**Task B 가 Task A 보다 훨씬 잘 된다.** 전선만 보고 추론 토큰 수를 상대오차 9~25%로 맞힌다.
라벨 붕괴(sonnet low≡medium, opus medium≡high)의 영향을 안 받기 때문이다 —
[[reasoning-effort-configured-vs-realized]] 의 "Realized 를 타깃으로" 방침이 수치로 확인됐다.

### Task C 는 provider 에선 거의 완전, 모델에선 거의 안 된다 <!-- (2026-11-20) -->
공통축, 전선 피처만, 문항 단위 2폴드.

| 과제 | 정확도 | 우연 |
|---|---|---|
| **3 provider 식별** | **99.2%** | 33.3% |
| 7 모델 식별 | 51.8% | 14.3% |
| OpenAI 내부 3모델 | 46.8% | 33.3% |
| Anthropic 내부 3모델 | **38.3%** | 33.3% |

혼동행렬에서 Google 은 725/725 완전 분리, Anthropic↔OpenAI 오분류는 40건(0.9%)뿐이다.
단독 피처로는 `down_bytes` 85.8%, `app_ttft_ms` 50.9%, 타이밍 3피처 71.8%.

**해석에 주의.** 99.2% 의 대부분은 **추론 신호가 아니라 프레이밍 오버헤드**로 보인다 —
`down_bytes` 절편이 Claude ~3,000B vs OpenAI ~11,500B 로 추론량 0에서도 4배 차이다.
즉 "응답을 어떻게 포장하느냐"가 갈리는 것이지 "얼마나 생각했느냐"가 갈리는 게 아니다.
**이것이 오히려 Task A/C 분리 논증을 강화한다**: provider 지문은 쉽게 읽히지만
같은 provider 안에서 모델을 가르는 건 우연보다 조금 나은 수준(38~47%)에 그치므로,
Task A 의 성능이 모델 지문을 베껴 쓴 것이라고 말할 수 없다.

**교란 미배제:** 모델마다 캡처 시각이 다르다(11-18 아침 ~ 11-20 새벽). 망 상태 변동을
provider 차이로 잘못 읽었을 가능성을 배제하지 못했다. 바이트 절편 차이는 시각과 무관하지만
TTFT 계열은 영향을 받을 수 있다. **한 pcap 안에서 모델을 교차로 찍는 캡처가 필요하다.**

### 모델마다 '뭉개는 단계'가 다르다 <!-- (2026-11-20) -->
같은 문항 안에서 인접 두 단계의 추론토큰을 비교했다(증가/동률/감소).

| 모델 | low→medium | medium→high | high→xhigh | xhigh→max |
|---|---|---|---|---|
| claude-sonnet-5-5 | 증74 / **동157** / 감19 | 증198/동17/감35 | 증198/동6/감46 | 증248/동1/감1 |
| claude-opus-5-5 | 증31/동1/감9 | **증26/동1/감14** | 증29/동1/감11 | 증41/동0/감0 |
| gpt-6-luna | 증182/동6/감62 | 증154/동6/감90 | 증151/동6/감93 | 증159/동2/감89 |
| gpt-6.1-sol | 증162/동11/감44 | 증223/동1/감17 | 증218/동3/감28 | 증236/동0/감14 |

**Anthropic 과 OpenAI 의 실패 양상이 질적으로 다르다.**
- **sonnet 은 `low` 와 `medium` 을 250문항 중 157개(63%)에서 완전히 같은 값으로 처리한다.**
  동률이지 역전이 아니다 — 두 라벨이 같은 설정에 매핑된다는 뜻이다.
  (opus 는 같은 현상이 `medium`↔`high` 에서 난다. 붙는 쌍이 모델마다 다르다.)
- **OpenAI 는 동률이 거의 없다(1~11건). 대신 역전이 많다**(luna `medium`→`high` 90/250 감소).
  설정은 매번 반영하되 분산이 크다는 뜻이다.

**탐지 쪽 함의가 반대다.** 동률은 반복 관측으로도 못 가르지만(정보가 없다),
역전은 같은 조건을 여러 번 보면 평균으로 걷힌다. **OpenAI 쪽이 다중 관측 가정에서는 더 유리하다.**

### `answer_tokens` 컬럼은 `output_tokens` 복사본이다 — 통제 검증에 쓰면 안 된다 <!-- (2026-11-20) -->
`parse_pcap.py` 가 내는 CSV 의 `answer_tokens` 는 **전 7모델 9,812행에서 `output_tokens` 와 완전히 같다.**
이름과 달리 추론 토큰이 빠져 있지 않다. Anthropic·OpenAI 는 `output_tokens` 안에 추론 토큰이 포함되므로
이 컬럼으로 "조건 간 출력 길이가 같은가"를 보면 **조건이 올라갈수록 커지는 가짜 통제 실패**가 보인다
(haiku 91 → 883). Gemini 만 `output_tokens` 가 추론을 제외해서 1 로 나온다 — provider 별 API 차이다.

**출력 길이 통제는 `answer_chars` 로 검증한다.** 순응 행의 중앙값이 전 모델·전 조건에서 정확히 1이다.
