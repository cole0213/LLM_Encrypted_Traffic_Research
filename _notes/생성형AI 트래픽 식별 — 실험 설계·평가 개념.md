# 생성형AI 트래픽 식별 — 실험 설계·평가 개념

상위: [[생성형AI 트래픽 식별]] · [[생성형AI 트래픽 식별 — L4 연구 로드맵]]

## 핵심 요약
L4 실험을 정직하게 설계·평가하기 위한 개념 정리(2026-09-01, 규상과 문답). 데이터 누수 방지 split, 샘플 단위, 현실 배포(segmentation), 슬라이딩 윈도우, 자율 에이전트.

## 샘플 단위와 flow (파일럿 실측)
- 파일럿 pcap 확인: **TCP 연결이 1개**(SYN 1번). Gemini SDK가 HTTP/2 keep-alive로 한 연결을 72요청에 재사용.
- 그래서 **flow(연결)는 1개**, 우리는 **시간(요청 간 4초 gap)으로 잘라 72개 "턴"**으로 나눔.
- **분류 단위 = 요청-응답 턴** (질문×조건 1개). flow 단위 아님.
- 현실 공격자도 지속 연결 하나를 idle gap으로 턴 분리 → 우리 시간분할이 그걸 흉내.

## train/test split과 데이터 누수
- split = 라벨 데이터를 train(학습)/test(평가)로 나눔. **평가 방법론이지 배포 행위 아님.**
- 누수(leakage) = test에 train과 너무 비슷한 게 섞여 정확도 뻥튀기(외우기).

### per-flow split
- flow = 한 연결/대화. 패킷 수백 개 뿜음.
- 나쁜 per-packet split = 패킷을 랜덤 분할 → 같은 flow 패킷이 train·test에 갈림 → SeqNo 등 flow-ID를 shortcut으로 악용 = 누수. ([[생성형AI 트래픽 식별 — baseline 문헌분석]]의 "Sweet Danger of Sugar": per-packet 98% → per-flow 40%).
- per-flow split = 한 flow는 통째로 한쪽에. **우리는 flow가 1개라 적용 불가** → 대신 질문별 split.

### 질문별(question-based) split
- 우리 샘플=턴. 한 질문이 여러 턴(3조건×3반복=9턴).
- 나쁜 랜덤 split = 같은 질문 턴이 train·test에 갈림 → "질문 트래픽 모양 외우기" = 누수.
- 질문별 split = 한 질문의 턴은 통째로 한쪽. 예: train=질문0~5, test=질문6~7(**처음 보는 질문**).
- 의미 = "**새 질문·프롬프트에서도 추론 깊이 맞히나**" = 현실 배포 성능의 정직한 추정치. (사용자는 늘 새 질문을 던지니까)
- 공통 원리: **내용 단위(flow/질문)를 쪼개지 말고 통째로 한쪽에.**

## 평가 split ≠ 배포 segmentation (혼동 주의)
- **질문별 split = 연구실 채점법.** 현실에선 안 함.
- **현실 배포 = flow 관측 → 턴 segmentation(경계 찾기) → 각 턴 분류.**
- 질문별 split 점수가 "현실서 나올 숫자"를 예측해줄 뿐, split 자체는 현실 행위가 아님.

## 현실 segmentation 가능성 (내 판단, 실측 아닌 추론)
- **인간 대화형: 대체로 가능** — 턴 사이 idle gap(사람 읽는 시간) + 방향 패턴(작은 상향 질문 → 큰 하향 응답)이 경계. WFP·음성지문·"Hello GenAI?"가 유사하게 함.
- **자율 에이전트: 어려움** — 아래.
- **완벽 범용 segmentation은 열린 문제.** 단 우리 신호가 "긴 침묵 이벤트"라 완벽 분리 없이도 잡힐 여지.
- 연구 전략: ①clean 분리(파일럿, 완료) → ②idle-gap 분리(인간 채팅) → ③분리-불요(슬라이딩 윈도우, 자율 에이전트) → 남는 건 future work.

## 자율 에이전트 (autonomous agent)
- 사람이 매 요청 X. LLM이 스스로 연속으로 요청·도구호출을 돌림(예: 버그수정 시 파일읽기→수정→테스트→재수정 수십 회). Claude Code·Cursor·Devin.
- 트래픽 분리 어려움: 요청 간 gap 거의 0(기계 속도), 도구호출 뒤섞임 → 턴 경계 안 보임.
- 역설: 분리는 어렵지만 **"빽빽한 연속 리듬" 자체가 인간과 구별되는 지문** → "자율이냐 아니냐"(L5) 판별은 오히려 쉬울 수 있음.

## 슬라이딩 윈도우 분류 (sliding window classification)
- 턴을 정확히 자르는 대신 **고정 시간창(W)을 스텝(S)씩 밀며 각 창을 분류.** 경계 몰라도 됨. (음성·행동인식 표준)
- 절차: 창 W=5s·스텝 S=1s → [0-5][1-6][2-7]... → 각 창 피처(패킷수·바이트·상하향비·최대gap·IAT) → 분류 → 연속결과 smoothing → "12-18초 깊은추론" 이벤트로.
- 장점: segmentation 불필요, 연속스트림·자율에이전트 적용, 실시간. 단점: W 민감, 겹친 창 중복, 창-턴 정렬 애매.
- 우리 궁합: "깊은 추론 = 긴 침묵 gap" → 창이 "비정상 침묵" 담으면 탐지 → 경계 없는 자율 에이전트에도 통함.

## ★ 타이밍 리듬 신호의 한계 — 재정리 (2026-09-02, 규상 비판)
**규상 지적(정타): 턴 간격(gap)은 사용자마다 다르다 → human/agent를 리듬으로 가르는 건 취약.**
- 빠른 파워유저 ≈ 에이전트 gap(짧음), rate-limit 걸린 에이전트 ≈ 사람 gap(김). **gap은 사용자 편차 = 신호 아니라 노이즈.**
- interactive 에이전트 사용(사람이 턴마다 몲, 예: Cursor·현재 세션)은 사람 리듬 → 회색지대라 실루엣으로 못 가름.
- **깨끗한 경우 = 완전 자율(사람이 loop에 아예 없음) 뿐.** 근데 그게 애초 우리가 잡고 싶은 것(남용 봇)이라 스코프가 올바르게 좁혀짐.

### 결론(방향 재정리)
- **폐기:** 타이밍 gap으로 human vs agent 분류 (사용자 편차).
- **핵심 유지:** **L4 턴별 추론깊이(96%, 사용자 무관=태스크가 정함, 검증됨)** = 논문 기둥.
- **에이전트 탐지 = 응용/확장인데, "완전 자율 loop의 구조"로 좁히고 실측 검증 후 판단.** 타이밍 말고 구조 신호로. bot detection과 차별점 = LLM 특유(추론버스트+도구결합).
- 안 되면 응용 축소하고 L4로 집중 — 그것도 정직한 결과.

### "완전 자율 loop의 구조"란 (타이밍 아닌, 사람이 못 만드는 것)
자율 에이전트 = 사람 개입 없이 **생각(reason)→도구호출(act)→결과관찰(observe)→생각→...** 반복(ReAct loop). 트래픽에 남는 구조적 지문(타이밍 무관·사용자 무관):
1. **다중 목적지:** LLM서버 + 도구서버들(웹검색·코드샌드박스·DB) 트래픽이 번갈아. 인간 채팅 = LLM 하나랑만. 도구 트래픽 없음.
2. **인과 결합:** LLM응답→(기계가 파싱)→도구호출→도구응답→LLM호출. **사람 결정 gap 없이 인과적으로 사슬처럼 엮임.** 인간은 LLM응답→(사람 판단)→LLM요청(도구 없음).
3. **지속·규모:** 수십~수백 스텝 연속(사람은 2분에 50번 도구왕복 물리적으로 불가).
4. **규칙성/자기유사:** reason-act-observe 모티프 반복 → 구조가 규칙적. 인간은 불규칙.
→ 즉 "**얼마나 빠르냐**"(타이밍, 사용자편차)가 아니라 "**LLM↔도구가 사람 없이 사슬로 엮여 지속 반복되는 배치**"가 신호. 이건 사람이 물리적으로 못 만들어서 사용자 무관.
