# CSTNET 패킷 시퀀스 LightGBM 실험

## 핵심 요약

CSTNET TLS 1.3의 120개 도메인·46,391 flow를 대상으로, 불완전한 `ws_col_info` 스니펫 대신 원본 PCAP의 패킷 순서를 LightGBM 피처로 만들었다. 순서 시퀀스는 랜덤 분할에서 **89.22%**, 캡처 순서 대리 holdout에서 **89.42%** Accuracy를 보였다. 집계 피처만 쓴 모델보다 각각 +8.32%p, +7.87%p 높다.

다만 현재 session_stat에는 기존 배포 45피처를 그대로 만들기 위한 시간·양방향 byte 일부가 빠져 있다. 따라서 이 문서의 시퀀스 모델은 아직 `45피처 + 시퀀스`의 최종 결과가 아니라, **PCAP 패킷 행동 자체가 CSTNET 도메인을 구분하는 강한 신호임을 확인한 단계**다.

관련: [[45피처 심층 분석 CSTNET]] · [[CSTNET CipherSpectrum 웹핑거프린팅]] · [[평가 프로토콜 P1 P2]]

## 데이터·운영 조건

- 데이터: CSTNET TLS 1.3, 120 클래스, 46,391 PCAP/flow.
- 실행: 서버16(`163.152.223.16`)에서만 실행.
- 입력: 서버16에 이미 존재하던 `/mnt/prism28/99_dataset/23_CSTNET_TLS1.3/02_session`. 새 Samba 마운트는 만들지 않았다.
- 모든 산출물: `Z:\nmlab\99_sgs\03_ML\lab_dashboard_ver0.1`에 대응하는 `/nmlab/99_sgs/03_ML/lab_dashboard_ver0.1` 아래에만 저장.
- 자원 제한: PCAP 추출은 `nice 12`, worker 6개. LightGBM은 `nice 12`, CPU 2스레드. 메모리 압박 시 즉시 종료 후 worker/스레드를 낮춘다.

## 완료된 실험

### 1. `ws_col_info` 스니펫 실험  <!-- (2026-07-27) -->

#### 이유

기존 45피처가 목적지 정보와 흐름 집계에 치우쳐 있어, SNI가 거의 없는 CSTNET에서 부족했다. `ws_col_info`의 일부 TCP 길이·window·재전송 정보를 붙여 패킷 행동의 유효성을 먼저 확인했다.

#### 결과

| 모델 | Accuracy | Macro-F1 | 해석 |
| --- | ---: | ---: | --- |
| 기존 45피처 | 69.43% | 65.76% | 목적지/흐름 통계만으로는 한계 |
| 45 + WS 통계 | 73.64% | 69.75% | TCP 전송 행동에 추가 신호 존재 |
| 45 + WS 순서 + 튜닝 | 76.82% | 73.08% | 짧은 순서 정보도 효과 있음 |

#### 해석과 한계

- `ws_win_min`, window, 방향 부호화 길이가 상위 gain이었다. 암호화 payload 대신 TCP 행동 패턴이 도메인 식별에 도움을 준다.
- 그러나 WS는 약 54%만 채워지고 평균 약 5패킷이라, 최종 입력으로는 범위·정보량 모두 부족하다.
- 이 결과가 원본 PCAP 전체 시퀀스 추출로 넘어간 이유다.

### 2. 원본 PCAP 표준 시퀀스 추출  <!-- (2026-07-27) -->

#### 이유

WS 스니펫 의존을 끊고, 데이터셋마다 동일하게 재현 가능한 패킷 순서 입력을 만들기 위함이다. 20/50/100개 패킷 길이 실험도 같은 산출물을 앞에서 잘라 재사용할 수 있어야 한다.

#### 방법

- 추출기: `lab_dashboard_ver0.1/extract_pcap_sequences.py`.
- TCP/UDP를 양방향 5-tuple flow로 묶고 client는 SYN 송신자(없으면 첫 패킷 송신자)로 정의.
- 패킷별: `packet_size`, `direction`, `iat_ms`, `tcp_window`, `retrans`, `payload_size`, `mask`.
- flow 메타: label, endpoint, 전체/저장 패킷 수, duration, burst 수·최장 burst, 업로드 비율, 재전송 수.
- 결과: **46,391 flow**, 오류 **0**, 10개 NPZ+CSV chunk, 약 26MB.
- 출력: `lab_dashboard_ver0.1/cstnet_seq_100_w6/`.

#### 해석

추출 중 RSS는 약 171MB 수준이었다. PCAP 재처리 자체는 6 worker로 안전하게 가능했고, 이후 모델 학습의 메모리 병목도 아니었다.

### 3. 시퀀스 LightGBM — 랜덤 8:2  <!-- (2026-07-27) -->

#### 이유

원본 시퀀스를 고정 길이 피처로 펼쳤을 때, 단순 집계보다 순서가 실제로 성능을 높이는지 빠르게 검증한다.

#### 피처

- 집계 29개: 크기·IAT·window·payload의 mean/std/min/max/sum, 재전송·패킷 수·방향 수, burst·duration 등.
- 순서 포함 529개: 집계 29개 + 앞 100개 패킷의 방향 부호화 크기, log IAT, TCP window, 재전송, 방향 부호화 payload.

#### 결과

| 모델 | 피처 수 | Accuracy | Macro-F1 |
| --- | ---: | ---: | ---: |
| 패킷 집계만 | 29 | 80.90% | 77.44% |
| 집계 + 100패킷 순서 | 529 | **89.22%** | **86.90%** |

- 결과: `lab_dashboard_ver0.1/cstnet_lgbm_sequence_v1.json`.

#### 해석

순서 피처의 이득은 Accuracy **+8.32%p**, Macro-F1 **+9.46%p**다. 패킷 크기·방향·타이밍의 순서가 단순 합계보다 훨씬 강한 도메인 행동 지문이라는 뜻이다.

#### 한계

같은 수집 풀의 클래스 층화 랜덤 분할이므로, 비슷한 세션이 train/test에 섞일 수 있다. 이 수치는 내부 분리 성능이지 배포 성능이 아니다.

### 4. 캡처 순서 대리 엄격 분할  <!-- (2026-07-27) -->

#### 이유

랜덤 분할 점수를 낙관적으로 해석하지 않기 위해, 각 도메인에서 파일 번호가 뒤인 20%를 시험으로 고정했다. 날짜 메타는 없으므로 완전한 LODO가 아니라 **캡처 순서 대리 holdout**이다.

#### 결과

| 모델 | Accuracy | Macro-F1 |
| --- | ---: | ---: |
| 패킷 집계만 | 81.55% | 78.06% |
| 집계 + 100패킷 순서 | **89.42%** | **87.07%** |

- 결과: `lab_dashboard_ver0.1/cstnet_lgbm_sequence_ordered_v1.json`.

#### 해석

- 순서 피처 이득은 Accuracy **+7.87%p**, Macro-F1 **+9.01%p**다.
- 랜덤 분할(89.22%)과 이 holdout(89.42%)이 비슷하다. 파일 번호가 시간 순서를 충분히 표현하지 못했거나, 패킷 지문이 이 데이터셋 안에서 안정적이라는 두 가능성이 있다.
- 따라서 “일반화가 증명됐다”가 아니라, **랜덤 분할만의 우연한 상승은 아닐 가능성이 커졌다** 정도로 해석한다.

## 현재 진행 중인 실험

### 5. 엄격 분할 기반 피처 조합·튜닝  <!-- (2026-07-28) -->

- 스크립트: `lab_dashboard_ver0.1/tune_cstnet_sequence_lgbm_ordered.py`.
- 실행 상태: 서버16에서 `nice 12`, 2스레드로 실행 중. RSS 약 1GB 수준, 가용 메모리 약 13GB 이상으로 안정적.
- 비교 조합:
  1. 집계만
  2. 앞 20패킷 + 모든 채널
  3. 앞 50패킷 + 모든 채널
  4. 앞 100패킷 + 크기·IAT만
  5. 앞 100패킷 + 모든 채널
  6. 앞 100패킷 + 모든 채널 + LightGBM 튜닝
- 튜닝 조합: trees 1,200, learning rate 0.03, leaves 127, min child 20, colsample 0.7, L2 5.
- 첫 실행은 하이퍼파라미터 중복 전달 오류로 결과 저장 전에 중단됐고, 메모리 문제는 아니었다. 기본값과 override 병합 방식으로 수정해 자동 재실행 중이다.

## 다음 자동 실험

1. 현재 조합·튜닝 결과에서 가장 작은 피처 수로 성능을 유지하는 조합을 선택한다.
2. 원본 PCAP에서 기존 45피처에 필요한 누락 흐름 통계(`ts_first`, duration, fwd/bwd packet·byte 등)를 재구성한다.
3. `기존 45피처`, `시퀀스 최선 조합`, `45피처 + 시퀀스`를 동일한 엄격 분할에서 비교한다.
4. 목적지 정보의 영향을 분리하기 위해 SNI/IP 포함·제외 조건을 별도 비교한다.
5. 날짜 또는 수집 세션 메타를 확보할 수 있으면 파일 번호 대리 holdout을 실제 날짜·세션 holdout으로 교체한다.
6. 결과가 확정되면 최선 모델·피처 스키마·재현 명령을 고정하고, `[[45피처 심층 분석 CSTNET]]`과 `[[CSTNET CipherSpectrum 웹핑거프린팅]]`을 갱신한다.

## 결론

현재까지의 가장 강한 결론은 “CSTNET에서 목적지 정보가 부족해도, 완전한 원본 패킷 시퀀스는 LightGBM으로 충분히 큰 추가 신호를 제공한다”이다. 목표는 92% 숫자 자체가 아니라, 이 개선이 목적지 반복을 외운 결과가 아닌지 더 엄격한 분할과 45피처 결합으로 검증하는 것이다.
